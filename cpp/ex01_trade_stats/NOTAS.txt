2. REFATORAÇÃO 1 — LINKAGE INTERNO (namespace anônimo)
--------------------------------------------------------------------------------

O QUE MUDOU
  `struct Trade` e as quatro funções de estatística (`mean_price`, `vwap`,
  `min_price`, `max_price`) passaram para dentro de um `namespace { ... }`
  sem nome, fechado com `}  // namespace` logo antes do `main`.

O PROBLEMA QUE ISSO RESOLVE
  Toda função e todo tipo declarado no escopo de arquivo, por padrão, tem
  LINKAGE EXTERNO: o símbolo entra na tabela do objeto (.o) e fica visível
  para o linker no programa inteiro. Consequências:

    a) Colisão de nome. Se um dia ex02 tiver outro `max_price` e os dois
       objetos forem linkados juntos, isso é uma violação da ODR (One
       Definition Rule). No melhor caso o linker acusa "duplicate symbol";
       no pior caso — funções `inline` ou template — ele escolhe uma das
       duas em silêncio e o programa faz a coisa errada em produção.
    b) Otimização perdida. Símbolo externo é, do ponto de vista do
       compilador, potencialmente chamado de fora da unidade de tradução.
       Ele não pode assumir que conhece todos os call sites, então inlining
       agressivo e eliminação de código morto ficam limitados. Em código de
       latência isso importa de verdade.

  Nada aqui é usado fora do main.cpp. Declarar externo é dar visibilidade
  global de graça, sem receber nada em troca.

POR QUE `namespace { }` E NÃO `static`
  As duas formas dão linkage interno para FUNÇÕES, e para função o efeito é
  equivalente. Escolhi o namespace anônimo por três razões:

    1. `static` em escopo de arquivo é herança do C. Em C++ a palavra
       `static` já significa outras três coisas (membro de classe, variável
       local persistente, método estático); sobrecarregar ela com um quarto
       sentido piora a leitura.
    2. `static` NÃO se aplica a tipos. Não existe `static struct Trade`.
       O namespace anônimo aplica-se a tudo — struct, função, template,
       variável — com uma construção só. Como o clang-tidy pediu o mesmo
       tratamento para o `Trade` logo em seguida, o namespace já cobria o
       caso; a versão com `static` teria exigido duas soluções diferentes
       no mesmo arquivo.
    3. É um bloco único: tudo que está lá dentro é privado ao arquivo, e
       isso fica óbvio na leitura. Com `static` a informação fica pulverizada
       em N palavras-chave que é fácil esquecer de repetir na função nova.

  Detalhe técnico: o namespace anônimo não é literalmente "sem nome" — o
  compilador gera um nome único por unidade de tradução e insere um
  `using namespace` implícito. Por isso os símbolos continuam acessíveis
  dentro do arquivo, mas nenhum outro .cpp consegue nomear aquele namespace.

DECISÃO DE ESCOPO
  O aviso original citava só `max_price`. Corrigi as quatro funções de uma
  vez porque as outras três têm exatamente o mesmo defeito — o linter só não
  as citou na mesma passada. Corrigir uma e deixar três acusando na próxima
  rodada é trabalho repetido.

ATUALIZAÇÃO (08/set, sessão dos testes) — LEIA JUNTO COM A SEÇÃO 7
  O namespace anônimo saiu. NÃO é regressão, é a mesma regra aplicada a um fato
  novo: `Trade` e as quatro estatísticas mudaram de arquivo, foram para
  `trade_stats.cpp`, e agora são chamadas de OUTRA unidade de tradução (o
  binário de teste). Linkage interno significa exatamente "ninguém fora deste
  .cpp pode me chamar" — mantê-lo tornaria o código intestável.

  A regra que vale, e que é a resposta de entrevista: o linkage deve ser o menor
  que ainda atende os call sites REAIS. Enquanto o único call site era o `main`
  do mesmo arquivo, o mínimo era interno. Assim que o teste virou call site
  legítimo, o mínimo passou a ser externo. Mudou o requisito, não o critério.

  O que sobrou de linkage interno: o `namespace { }` dentro de
  `tests_trade_stats.cpp`, que guarda os helpers do teste (`kGabarito`,
  `parse()`). Esses sim não são chamados de lugar nenhum.

      /Library/Developer/CommandLineTools/usr/bin/clang-format

4. REFATORAÇÃO 3 — ALVOS `format` E `format-check` NO CMake
--------------------------------------------------------------------------------

O QUE MUDOU
  `cpp/CMakeLists.txt` ganhou dois alvos customizados:

      cmake --build build --target format        # reescreve in-place
      cmake --build build --target format-check  # só verifica, falha se sujo

POR QUE VIROU ALVO DE BUILD E NÃO UM ALIAS DE SHELL
  Um alias no ~/.zshrc some quando eu troco de máquina e não existe para
  ninguém que clone o repo. Alvo de CMake viaja junto com o código.

DECISÕES DENTRO DO BLOCO

  find_program(... HINTS ...)
    Por causa da pegadinha da seção 3, o `find_program` puro não acharia o
    binário. Os HINTS cobrem Command Line Tools + LLVM do Homebrew em ARM
    (/opt/homebrew) e Intel (/usr/local).

  if(CLANG_FORMAT_BIN) ... else() message(STATUS ...) endif()
    Se o binário não existir, o CMake apenas avisa e não cria os alvos. A
    alternativa — `message(FATAL_ERROR)` — quebraria o `cmake -S . -B build`
    de quem só quer COMPILAR o projeto numa máquina sem clang-format.
    Ferramenta de higiene não pode ser pré-requisito de build.

  file(GLOB_RECURSE ... CONFIGURE_DEPENDS)
    Glob em CMake normalmente é má prática para LISTA DE FONTES de um alvo,
    porque o arquivo novo não dispara reconfiguração e o build fica
    silenciosamente desatualizado. Aqui o caso é outro: a lista alimenta um
    formatador, não a compilação. O custo de errar é "arquivo novo não foi
    formatado", não "binário errado". Somado a isso, `CONFIGURE_DEPENDS`
    manda o CMake refazer o glob quando arquivos aparecem ou somem. Com isso
    ex02, ex03... entram no `format` sozinhos — que é exatamente o que quero
    num repo de estudo que ganha um diretório por dia.

  list(FILTER FORMAT_SOURCES EXCLUDE REGEX "/(build|cmake-build-[^/]*)/")
    Os diretórios de build (`build/` do CLI, `cmake-build-debug/` do CLion)
    ficam DENTRO da árvore de fontes. Sem esse filtro o glob pegaria código
    gerado e artefatos de terceiros. O `cmake-build-[^/]*` casa também
    `cmake-build-release`, `cmake-build-relwithdebinfo` etc.

  VERBATIM
    Garante que os caminhos passados ao comando sejam escapados corretamente.
    Sem isso, um caminho com espaço (bem provável em macOS) quebra o alvo.

  Por que DOIS alvos
    `format` corrige, `format-check` só acusa e sai com código != 0
    (`--dry-run -Werror`). O segundo é o que serve para CI ou pre-commit
    hook: em pipeline eu quero FALHAR, não quero um passo que altera
    arquivos no meio do build.

6. CONCEITOS DO DIA — RESPOSTAS PRONTAS PARA ENTREVISTA
--------------------------------------------------------------------------------

RAII (Resource Acquisition Is Initialization) — apontando para o `ifstream`
  O tempo de vida do RECURSO é amarrado ao tempo de vida do OBJETO. O
  `std::ifstream file(argv[1])` abre o arquivo no construtor e o fecha no
  destrutor, que o compilador chama automaticamente quando `file` sai de
  escopo. Ninguém escreve `close()` e é impossível esquecer. O ponto forte
  é que isso vale inclusive no caminho de exceção: se o `std::stod` lançar
  lá dentro do loop e a exceção propagasse para fora da função, o
  desempilhamento (stack unwinding) chamaria o destrutor do `file` no
  caminho. Em C, com `fopen`/`fclose`, todo `return` antecipado é uma chance
  de vazar o handle.

`const std::vector<Trade>&` nos parâmetros
  O `&` evita copiar o vector inteiro a cada chamada — passar por valor
  copiaria todos os elementos (alocação no heap + cópia). O `const` é a
  promessa, verificada pelo compilador, de que a função só lê. Os dois
  juntos dão o desempenho de passar ponteiro com a segurança de passar cópia.

Linkage interno vs externo
  Ver seção 2. Resumo de 30 segundos: linkage externo expõe o símbolo ao
  linker do programa inteiro, o que abre porta para violação de ODR e
  bloqueia otimização; namespace anônimo restringe à unidade de tradução.

7. SESSÃO 08/set — TESTES COM Catch2
--------------------------------------------------------------------------------

O PRÉ-REQUISITO QUE NINGUÉM AVISA
  Não dava para testar nada sem antes mexer na estrutura. Função que mora ao
  lado do `main()`, dentro do executável, não tem como ser chamada por um
  segundo binário — o binário de teste tem o `main()` dele. Ou o teste é só
  caixa-preta (roda o processo e compara stdout), ou a lógica sai do executável.

  Escolhi tirar a lógica: `trade_stats.hpp` + `trade_stats.cpp` viraram uma
  biblioteca (`trade_stats_lib`), e tanto o executável quanto os testes linkam
  contra ela. O `main.cpp` encolheu para ~30 linhas de puro cabeamento de CLI:
  checar argc, abrir arquivo, chamar `parse_trades`, imprimir.

  Benefício de tabela: o parsing saiu junto, como
  `parse_trades(std::istream&) -> ParseResult{trades, malformed}`. Recebendo
  `istream` em vez de caminho de arquivo, o teste alimenta um
  `std::istringstream` e não toca em disco. Teste que depende de arquivo falha
  por motivo errado (cwd errado, permissão) e esconde a regressão de verdade.

DECISÕES NO CMake

  option(FTE_BUILD_TESTS ... ON)
    Com OFF, o bloco inteiro do FetchContent é pulado e o projeto compila sem
    rede. FetchContent baixa no CONFIGURE, então sem essa saída um avião ou um
    wifi ruim impediriam até de compilar o exercício. Verificado: configure,
    build e rodada do binário funcionam com -DFTE_BUILD_TESTS=OFF.

  Sanitizers continuam GLOBAIS, warnings viraram alvo INTERFACE
    Esta foi a mudança estrutural do CMakeLists. Antes, `-Wall -Wextra
    -Wpedantic -Werror` e os sanitizers eram dois `add_compile_options()`
    globais. Com uma dependência de terceiros na árvore, isso quebra:

      - `-Werror` global aplicado ao Catch2 = build falha por warning que não é
        meu e que eu não posso consertar. Por isso virou
        `add_library(project_warnings INTERFACE)`, linkado só nos meus alvos.
      - Sanitizer, ao contrário, PRECISA continuar global e pegar o Catch2
        junto. Misturar código instrumentado com não instrumentado faz o ASan
        emitir falso positivo de container-overflow quando um
        `std::vector`/`std::string` cruza a fronteira entre os dois mundos.

    Ou seja: duas flags que antes andavam juntas têm escopos opostos assim que
    entra dependência externa. Boa pergunta de entrevista escondida aqui.

  SYSTEM no FetchContent_Declare
    Marca os headers do Catch2 como headers de sistema. Sem isso, o
    `tests_trade_stats.cpp` — que É compilado com `-Werror` — quebraria por
    warning gerado dentro das macros do Catch2. Precisa de CMake >= 3.25.

  GIT_TAG v3.16.0 (tag fixa, não branch) + GIT_SHALLOW
    Build reproduzível não segue `devel`. Fixar a tag é o que garante que o
    build de hoje e o de daqui a seis meses baixam o mesmo código.

  catch_discover_tests()
    Registra cada TEST_CASE como um teste individual no CTest, em vez de um
    único caso "roda o binário". No relatório aparece QUAL caso caiu — que é a
    diferença entre sinal útil e "o teste falhou, vai investigar".

  Glob do `format` ganhou `_deps` na exclusão
    O FetchContent despeja as fontes do Catch2 em `build/_deps/`. Já estava
    coberto pelo filtro de `build`, mas explicitei — se um dia eu mudar
    FETCHCONTENT_BASE_DIR, o filtro continua valendo. Confirmado no log do
    alvo: o clang-format recebeu só os meus 4 arquivos.

OS TESTES (10 casos, `ex01_trade_stats/tests_trade_stats.cpp`)
  parse: linhas boas; linha sem vírgula; preço não numérico; qty não numérica;
  campo vazio dos dois lados da vírgula; malformada no fim sem newline final (o
  caso exato do `trades.csv`); stream vazio; só lixo.
  stats: gabarito conferido na mão; VWAP != média quando as qty diferem;
  VWAP == média quando as qty são iguais; trade único; min/max independentes da
  ordem de entrada.

  Um dos testes documenta um comportamento que eu não sabia que existia:
  `std::stod`/`std::stol` PARAM no primeiro caractere inválido e não lançam.
  "101.50abc" vira 101.50 em silêncio e o parser aceita. O teste registra o que
  o código faz HOJE — se um dia isso virar erro explícito, ele falha e a decisão
  aparece, em vez de passar despercebida.

O TESTE DOS TESTES (mutation testing na mão)
  Suíte que passa não prova nada; suíte que nunca falha é decoração. Quebrei o
  código de propósito, três vezes, e conferi que a suíte pega:

    `<` virou `>` em min_price ....... cai "min e max nao dependem da ordem"
    vwap ignorando a quantidade ...... cai "vwap difere da media simples"
    parse sem contar malformada ...... cai "so com lixo nao produz trade valido"

  Restaurado o código, 10/10 voltam a passar. Vale virar hábito: teste novo só

8. PENDÊNCIAS / O QUE FICOU DE PROPÓSITO
--------------------------------------------------------------------------------

- `trades.csv` tem uma última linha com o literal "dfgdrgrgrgrg" e sem newline
  final. É intencional: é a fixture que exercita o contador de malformadas
  (linha sem vírgula → `find` devolve `npos`). Agora esse caso também está
  coberto por teste unitário, com o mesmo literal, então o CSV virou redundância
  de conveniência — dá para limpá-lo sem perder cobertura, se um dia incomodar.

- Min/max continuam escritos na mão, com laço explícito, porque o enunciado do
  dia 1 pede isso. Em código de produção seriam `std::ranges::minmax_element`
  numa passada só — hoje são duas passadas sobre o mesmo vector. Otimização
  deliberadamente não feita: o exercício treina o laço. Com a suíte no lugar,
  agora dá para trocar a implementação com rede de segurança — bom exercício
  para quando a Fase 0 chegar em STL/algorithms (S3).

- Vector vazio continua sendo PRECONDIÇÃO das quatro estatísticas, documentada
  no `trade_stats.hpp` e garantida pelo guard no `main`. Não há teste para o
  caso vazio porque o comportamento é UB (min/max acessam trades[0]; mean/vwap
  dividem por zero) — testar UB é testar sorte. A alternativa real seria mudar a
  assinatura para `std::optional<double>` ou `std::expected`; fica para a S4,
  que é onde o roadmap trata error handling.

- Não há teste de ponta a ponta do binário (argv, exit code, texto no stderr).
  Os 10 casos cobrem lógica, não cabeamento. Os quatro caminhos de CLI seguem
  verificados à mão. Candidato natural a um `add_test` do CTest chamando o
  executável.

- `format-check` e `ctest` ainda não estão plugados em hook nem CI. Os alvos
  existem; o gatilho não.
