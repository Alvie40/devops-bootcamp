# ClinGate — Security and Compliance Design

**Draft v0.1 · 2026-09** · Companion to [SPEC.md](SPEC.md) and [LOADTEST.md](LOADTEST.md)

> This document maps controls to frameworks so the design can be **discussed and
> tested**. It does **not** claim HIPAA, ISO 27001, SOC 2, IEC 62304 or FDA
> compliance. ClinGate is a lab, not a medical device, and handles synthetic data only.

---

## 1. Data classification and handling rules

| Class | Examples | Rules |
|---|---|---|
| **Synthetic PHI-shaped** | Observations, pseudonymous subject IDs, HL7 messages | Treated **as if real**: encrypted at rest/in transit, tenant-isolated, audited. Generated by a seeded generator only. |
| **Direct identifiers** | HL7 `PID-5/7/11`, names, addresses | **Dropped at parse time**; never stored, queued, or logged. |
| **Operational** | Metrics, non-PHI logs, IaC | Normal handling; still no secrets in git. |

Hard rules:

1. **No PHI in logs, metrics, traces, queue bodies, or error messages.** Logs use a
   field allow-list; parsers never log message bodies. Before logging any new field, ask
   whether it could identify a subject.
2. **No real data** in any environment, including dev on NavyBlue.
3. **Pointers, not payloads** in SQS.
4. **Pseudonyms only**: the platform never holds the mapping to real identities.

## 2. Trust boundaries and threat model (STRIDE)

| Boundary | Threat (STRIDE) | Control | Test |
|---|---|---|---|
| Internet → ALB / `ingest-api` | **S**poofing a device | Cognito M2M JWT, scope check, client→tenant resolution | Expired/forged/wrong-audience token rejected |
| | **T**ampering in transit | TLS 1.2+, HSTS; SHA-256 checksum stored with raw | Downgrade attempt fails |
| | **R**epudiation | Audit event per request (client, tenant, request ID) | Audit row exists for every accepted request |
| | **I**nfo disclosure | Tenant RLS; generic error bodies; no PHI in logs | Cross-tenant read returns nothing; log scan for identifiers |
| | **D**oS | Body/field limits, per-client quota → `429`, WAF (optional), queue absorbs | Oversize/slow-body tests; quota test |
| | **E**levation | Scopes least-privilege; operator reads need MFA user | `ingest:write` token cannot call read endpoints |
| Partner → NLB / `mllp-listener` | Spoofing | mTLS; cert fingerprint → client → tenant; `MSH-3/4` must match | Wrong cert / mismatched `MSH` → `AR` |
| | Tampering / injection | Strict parser, size + segment + field limits, no dynamic eval, fuzzing | Fuzz corpus; malformed-frame suite |
| | DoS (slowloris on TCP) | Idle/read timeouts, per-client connection cap | Slow-sender test |
| | Info disclosure | Direct identifiers dropped; `AE`/`AR` text is generic | Identifier fields absent everywhere |
| Pod → AWS APIs | Credential theft | IRSA (short-lived), least-privilege policies per component, no static keys | IAM policy simulation; Access Analyzer |
| | Exfiltration | S3/KMS policies scoped to component roles; VPC gateway endpoint for S3 | Denied-access tests |
| Worker → Aurora | Cross-tenant access | RLS (`FORCE`), `app_rw` not owner, `SET LOCAL` per txn | Negative RLS test in CI |
| CI → AWS | Token abuse | GitHub OIDC with `sub` conditions (repo + ref/environment); separate staging/prod roles; actions pinned by SHA | Trust-policy tests; unpinned action fails lint |
| Human → AWS | Credential compromise | Identity Center SSO + MFA; no IAM users; SCP guardrails; break-glass documented | Access-key creation denied by SCP |
| Supply chain | Malicious dependency/image | SCA, SBOM, signed images, admission/verify, pinned base images | Unsigned image blocked at deploy |

## 3. Identity and access

- **Humans:** IAM Identity Center; permission sets `OrgAdmin` (management only),
  `Operator`, `SecurityAuditor` (read-only). Root: MFA, sealed.
- **CI:** GitHub OIDC → `gh-clingate-staging` and `gh-clingate-prod`. Trust policy pins
  `repo`, `ref`, and (for prod) the GitHub `environment`. Prod role is narrower.
- **Workloads:** IRSA (Fargate). One IAM role per component; e.g., `ingest-api` may
  `s3:PutObject` on the raw prefix and `sqs:SendMessage` on `ingest-q` — and nothing
  else. No component can read another's secrets.
- **Callers:** devices via Cognito M2M (scope `ingest:write`); operators via Cognito
  users with MFA (scope `records:read`); MLLP partners via client certificates.
  All three resolve to a `clients` row and a tenant.

## 4. Guardrails (SCPs) and detective controls

**SCPs (org level):** deny `organizations:LeaveOrganization` · deny disabling or
deleting CloudTrail / GuardDuty / Access Analyzer · deny actions outside an allowed
region list · deny creating IAM users or access keys · deny S3 public access changes ·
deny creating unencrypted S3/EBS/RDS · deny removing the audit archive's Object Lock.

**Detective:** organization CloudTrail (management events, log-file validation) into the
`security-tooling` archive · IAM Access Analyzer (external-access findings) ·
GuardDuty and Security Hub are **budget-gated options** (verify pricing/free tier) ·
nightly drift detection · nightly SBOM re-scan.

## 5. Cryptography and secrets

| Item | Design |
|---|---|
| At rest | KMS CMKs per account/environment (S3, Aurora, Secrets Manager, EBS/ephemeral); SQS uses SSE-SQS; annual rotation enabled |
| S3 | SSE-KMS with **Bucket Keys**; deny unencrypted PUT and non-TLS; `ChecksumSHA256` on every PUT |
| In transit | TLS 1.2+ everywhere; **mTLS** for MLLP in/out; internal AWS calls over TLS |
| Key policy | Key admins ≠ key users; components get `Encrypt/Decrypt/GenerateDataKey` on their own key only |
| Secrets | Secrets Manager (DB credentials with managed rotation); nothing in env files, images, or git (Gitleaks blocks) |
| Certificates | cert-manager with a lab CA; rotation runbook; prod-shape = partner-provisioned certs |
| Audit signing (stretch) | Daily digest of audit records signed with a KMS asymmetric key |

## 6. Compliance mapping (lab-level, for discussion)

### 6.1 HIPAA Security Rule — technical safeguards (§164.312)

| Requirement | ClinGate control |
|---|---|
| (a)(1) Access control | Identity Center, IRSA, Cognito scopes, tenant RLS, unique client identities |
| (b) Audit controls | `audit_events` (INSERT-only) + out-of-account Object Lock copy; separate audit log group |
| (c)(1) Integrity | SHA-256 checksums, versioned immutable raw store, idempotent exactly-once effect, reconciliation |
| (d) Person/entity authentication | Cognito JWT / MFA users / mTLS client certs |
| (e)(1) Transmission security | TLS 1.2+, mTLS for HL7 |

Administrative and physical safeguards are organizational and out of scope for a lab.

### 6.2 LGPD (Brazil)

Health data is sensitive personal data (art. 11); security measures (art. 46). The same
technical controls apply; pseudonymization and minimization are enforced in code
(direct identifiers dropped). Article references to verify.

### 6.3 21 CFR Part 11 (electronic records)

In scope: audit trail (§11.10(e)), record integrity, access controls. **Out of scope:**
electronic signatures (§11.50/11.70).

### 6.4 ISO 27001 / SOC 2

Controls map to common families (access, logging, change management, cryptography,
supplier/supply-chain, vulnerability management). The lab **operates the controls**;
it is not certified and has no ISMS/audit program.

## 7. Audit design

Two logs, deliberately separate:

1. **Application log** — errors, latency, no subject-level detail.
2. **Access/mutation audit log** — who (`actor_type`, `actor_id`, client/tenant), what
   (`action`, `resource`), which subject (pseudonym), why (`purpose`), outcome, request
   ID, source IP, timestamp.

Path: app → `/clingate/audit` CloudWatch Logs → Firehose → **S3 in `security-tooling`**
(Object Lock, separate KMS key, no delete permission for workload accounts). The
database keeps a queryable INSERT-only copy. Verification: reconciliation asserts
audit count ≥ reads issued in every load test.

## 8. Software supply chain

| Control | Detail |
|---|---|
| Pinned dependencies | Lock files; base images by digest; GitHub Actions by commit SHA |
| SBOM | Syft CycloneDX per image, stored as a cosign **attestation** (travels with the artifact) |
| Signing | cosign **keyless** via GitHub OIDC (no key material to manage); deploy verifies signature and identity |
| Provenance | Build provenance attestation (SLSA-style; level claim to verify) |
| Continuous re-scan | Nightly: stored SBOMs re-scanned against newly published CVEs → issue opened. This is the point of an SBOM: knowing whether a *new* CVE affects a *shipped* artifact without rebuilding. |
| Admission (stretch) | Policy controller enforcing "signed by our workflow" in-cluster; otherwise verified in the deploy job |
| Update flow | Dependabot/Renovate PRs through the same gates |

## 9. Secure SDLC gates and remediation policy

| Gate | Tool | Fails on | Proposed remediation SLA |
|---|---|---|---|
| Secrets | Gitleaks | Any finding | Rotate immediately; treat as incident |
| SAST | Semgrep + custom rules | ERROR severity | Fix before merge |
| SCA | Trivy fs | HIGH+ with a fix available | CRITICAL 7 d · HIGH 30 d (or documented exception) |
| IaC | Checkov/tfsec | HIGH+ | Fix before merge, or a dated `skip` with justification |
| Container | Trivy image | CRITICAL/HIGH | Rebuild on newer base within SLA |
| DAST | ZAP baseline | Reported | Triage per finding |
| Perf gate | k6 thresholds | Threshold breach | Blocks promotion |
| Fuzz/negative | Hypothesis/Atheris, pytest | Any crash/violation | Fix before merge |

SLAs are a proposed policy for the lab, not a claim about any employer's program.

## 10. Hazard and risk register (ISO 14971-style, data-integrity focus)

| ID | Hazard | Hazardous situation | Potential harm | Control | Verification |
|---|---|---|---|---|---|
| H1 | Lost observation | Result acknowledged but never stored | Missing clinical data | Durable-before-ack; DLQ; reconciliation | Every load test: sent = stored |
| H2 | Duplicate result | Retry double-applied | Skewed analytics/alerts | Idempotency keys; unique constraints; deterministic outbound `MSH-10` | Injected-duplicates test |
| H3 | Wrong subject | Cross-tenant/subject association | Privacy breach, wrong record | RLS; pseudonym per tenant; client→tenant binding | Negative RLS test; cert/`MSH` mismatch test |
| H4 | Silent corruption | Payload altered in transit/storage | Wrong values used | TLS; SHA-256 at PUT and re-verify in worker; versioning | Checksum mismatch → quarantine test |
| H5 | Undetected delay | Export backlog unseen | Stale data downstream | Queue-age alarms; export-lag SLI | Destination-slow chaos test |
| H6 | PHI disclosure via logs | Identifiers in log lines | Confidentiality breach | Field allow-list; log scan in CI | Log-scan test against fixtures |
| H7 | Unit/encoding error | Latin-1 mis-decoded; unit dropped | Wrong interpretation | Charset handling; unit required for numeric | Encoding fixtures |
| H8 | Malicious HL7 input | Crafted message crashes/abuses parser | Availability loss | Limits; fuzzing; `AR` on violation | Fuzz corpus in CI |

## 11. Security testing plan

- **Unit/property tests:** HL7 parser/builder round-trip; idempotency; ACK matrix.
- **Fuzzing:** Hypothesis/Atheris against framing, segment/field parsing, charset.
- **Negative/authz suite:** wrong tenant, wrong scope, expired token, wrong cert, mismatched `MSH`.
- **RLS test:** tenant A cannot read tenant B through any path.
- **Audit test:** every read produces an audit event with the right actor/subject.
- **DAST:** ZAP baseline on `ingest-api`.
- **IaC/container/SCA/secrets/SAST:** per SPEC §9.
- **Chaos-lite:** kill worker mid-message; slow/kill sink; revoke a client cert.
- **Not in scope:** formal pentest. A planned one would follow the AWS policy for
  penetration testing of your own resources (verify).

## 12. Incident response (outline)

| Scenario | First actions |
|---|---|
| Credential/key leaked | Rotate; revoke sessions; check CloudTrail for use; assess blast radius; history rewrite only if needed (breaks clones) |
| Suspected PHI exposure | Freeze affected path; preserve logs; identify scope from audit trail; notify per policy |
| Poison message flood | Confirm DLQ alarm; quarantine; fix parser; replay from raw |
| Compromised client cert | Disable `clients` row; rotate CA/cert; review that client's audit trail |
| Destination outage | Confirm backlog/age alarms; pause exports; redrive after recovery |

## 13. IEC 62304 lifecycle mapping (informational)

ClinGate is **not** medical device software; this table shows where its practices
would sit in a 62304-style lifecycle.

| Lifecycle activity | ClinGate practice |
|---|---|
| Planning (5.1) | SPEC.md, phase plan and exit criteria |
| Requirements (5.2) | FR/NFR IDs traced to tests |
| Architecture (5.3) | Diagrams, ADR log, component limits |
| Unit implementation/verification (5.5) | Unit + property tests, SAST, lint |
| Integration testing (5.6) | LocalStack/kind integration suite |
| System testing (5.7) | Load/stress/failure tests + reconciliation |
| Release (5.8) | Signed artifacts, SBOM, approval-gated promotion |
| Maintenance (6) | Nightly SBOM re-scan, drift detection, dependency PRs |
| Risk management (7) | §10 register (ISO 14971-style) |
| Configuration management (8) | Git, pinned deps, IaC, provenance |
| Problem resolution (9) | Issues from scans, DLQ/incident runbooks |

Traceability: each FR/NFR/hazard ID appears in test names (e.g., `test_FR3_ack_after_durable`,
`test_H2_duplicate_msh10`).
