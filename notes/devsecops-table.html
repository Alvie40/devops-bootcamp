01Gitleaks
Secrets
Secrets scanning — não é sigla: é a prática de detectar segredos (chaves, senhas, tokens) commitados no código ou no histórico do git antes que alguém os explore.
Como funcionaCLI em Go que varre o git log commit por commit (não só o working tree), aplicando regex + detecção de entropia contra padrões conhecidos (chave AWS, token Stripe/GitHub etc.) e regras próprias em TOML.
Como eu usogitleaks detect --source . --no-banner contra o repo inteiro. Plano: virar pre-commit hook, hoje ainda roda manual.
ResolveCredencial hardcoded commitada no git — some do arquivo, mas não do histórico.
Achado real0 leaks no repo real. Demo provocada (repo git descartável): removi a chave num commit "fix" e o Gitleaks ainda achou, apontando o commit antigo — git show confirmou que a chave inteira ainda existe lá.
Ações
implementadaRodei o Gitleaks contra o histórico real e provoquei um leak num repo descartável pra confirmar o comportamento.→ 0 leaks reais, causa raiz explicada
implementadaInstalei .pre-commit-config.yaml com o hook oficial do Gitleaks e testei nos dois sentidos: bloqueou uma chave AWS aleatória, deixou passar AKIAIOSFODNN7EXAMPLE (allowlist padrão — é o placeholder oficial da doc da AWS).→ hook ativo e validado
decisão: não fazerRotacionar uma credencial de verdade após um leak — exigiria um leak real de produção pra praticar em cima; risco não vale o exercício.
Vs. vaga da Casey (Analog Devices) implícita Não aparece como sigla isolada no anúncio, mas é a base de qualquer pipeline seguro — está implícita em "SSDLC" e em secrets management dentro de AWS (IAM/KMS), que a vaga cita.
leak provocado→detectado + causa raiz explicada
02Semgrep
SAST
SAST = Static Application Security Testing — analisa o código-fonte sem executá-lo, procurando padrões conhecidos de vulnerabilidade.
Como funcionaParseia o código numa AST (árvore de sintaxe) e casa "patterns" escritos numa DSL parecida com o próprio código-fonte contra essa árvore — é estrutural, não regex de texto, mas ainda depende de existir um pattern pro bug exato.
Como eu usosemgrep scan --config auto . no dia a dia. Quando acho um gap, escrevo regra própria em YAML e rodo --config auto --config minha-regra.yaml junto.
ResolveBug de segurança no código que você mesmo escreveu (injection, hash fraco, secret hardcoded).
Achado realRuleset padrão (auto) pegou 3 de 4 bugs plantados — perdeu os.system("..."+var), mesma classe de subprocess.call(shell=True), só com sintaxe diferente.
Ações
implementadaEscrevi uma regra Semgrep própria em YAML (pattern: os.system("..." + $VAR)) fechando exatamente o gap.→ 3 → 4 findings
pendenteAplicar os padrões de fix no código real (sem shell=True, hash com scrypt/bcrypt, secret em variável de ambiente) — hoje só existem no arquivo de demo.
Vs. vaga da Casey (Analog Devices) citada explicitamente SAST é uma das siglas do anúncio — um dos gaps centrais que o job-bot mapeou antes da candidatura, ao lado de DAST/SCA/SBOM.
3 findings→4 findings
03Trivy fs
SCA
SCA = Software Composition Analysis — audita as dependências de terceiros que o projeto importa, cruzando nome+versão com bancos de CVE conhecida.
Como funcionaLê o manifesto de dependências (requirements.txt, lockfile etc.), extrai nome+versão exata de cada pacote, e cruza contra um banco de CVE baixado e cacheado localmente — puro lookup, nunca analisa o código da lib em si.
Como eu usotrivy fs --scanners vuln . antes de subir uma dependência nova ou como gate de CI. Precisa de versão pinada (==) — range não é lido.
ResolveCVE conhecida em biblioteca de terceiros que o projeto importa — não é código seu, mas é seu risco.
Achado realrequests==2.6.0 / pyyaml==5.1 / urllib3==1.24.1 → 20 CVEs (3 críticas), incluindo RCE no PyYAML via FullLoader.
Ações
implementadaPinei versão corrigida exata (==) de cada lib e reescaneei.→ 20 → 0 CVEs
implementadaDescobri que range (>=) faz o Trivy nem escanear — só versão fixa funciona.→ virou regra pro time
implementadaConfigurei .github/dependabot.yml pra pip, base image do Dockerfile e GitHub Actions.→ atualização automática semanal
implementadaRodei o gate de SCA num PR real (#1) no GitHub Actions. O 1º run falhou por bug meu no workflow (tag trivy-action@0.28.0 inexistente — a certa é v0.36.0), corrigido.→ verde no CI
Vs. vaga da Casey (Analog Devices) citada explicitamente SCA está no anúncio ao lado de SAST/DAST/SBOM — mesmo bloco de gap mapeado pelo job-bot.
20 CVEs→0 CVEs
04Trivy image
Container
Container scanning — não é sigla: escaneia a imagem final (SO base + libs de sistema + app), não só o código-fonte que você escreveu.
Como funcionaMesma engine de CVE do Trivy fs, mas desmonta a imagem Docker camada por camada, lista os pacotes do SO instalados (dpkg/apk/rpm) + os pacotes de linguagem que estão dentro da imagem, e cruza tudo contra o mesmo banco de CVE.
Como eu usodocker build -t app:tag . seguido de trivy image --severity CRITICAL,HIGH app:tag. Comparo antes/depois toda vez que troco base image ou atualizo dependência.
ResolveVulnerabilidade herdada da imagem base (SO + libs de sistema) — invisível olhando só o código da app.
Achado realpython:3.11 completo = 654 CVEs críticas/altas, quase tudo do Debian base (não da app).
Ações
implementadaTroquei a base pra -slim.→ 654 → 62
implementadaAtualizei fastapi (puxou starlette sem CVE).→ 62 → 59
implementadaTentei atualizar pip/setuptools/wheel pra fechar as 2 CVEs restantes do Python.→ trocou por outras 2, sem ganho — revertido
implementadaMulti-stage Dockerfile.distroless — testado de pé, mas superado pela opção simples abaixo.→ 59 → 49 (2 CRITICAL)
implementadaapt-get upgrade (os CRITICAL do perl-base tinham fix) + remover setuptools/wheel (não usados em runtime). Adotado; mantém shell.→ 59 → 44, 0 CRITICAL, 0 com --ignore-unfixed
implementadaGate do CI com ignore-unfixed: bloqueia o que tem correção disponível; Fixed Version: None vira monitoramento.→ verde no CI
implementadaTrigger schedule (cron semanal) pra pegar patch na mesma tag da base image.→ rebuild toda segunda
residual sem fixOs 44 que sobram no slim endurecido não têm patch upstream ainda — confirmado pelo Trivy (--ignore-unfixed = 0). Não é pendência de esforço; o cron semanal reescaneia.
Vs. vaga da Casey (Analog Devices) implícita Não vem como termo isolado no anúncio, mas cai dentro do escopo cloud-native que a vaga cita via ECS/EKS — sem container scanning não dá pra rodar CVE-free nesse tipo de ambiente.
654→44slim endurecido: 44 (0 CRITICAL) · distroless: 49 · 0 corrigíveis restantes
05Syft
SBOM
SBOM = Software Bill of Materials — inventário formal de tudo que compõe o artefato (componentes, versões, licenças), pra responder rápido quando sai uma CVE nova.
Como funcionaTambém desmonta imagem/diretório como o Trivy, mas em vez de comparar contra CVE, só cataloga tudo que encontra (pacotes de SO, libs de linguagem, binários) e serializa num formato padrão (CycloneDX ou SPDX) — inventário puro, sem lookup de vulnerabilidade.
Como eu usosyft dir:. -o cyclonedx-json > sbom.json depois de cada build. Objetivo: publicar como artefato do CI, não gerar manual.
ResolveSem inventário, uma CVE nova (ex.: Log4Shell) exige re-escanear tudo do zero pra saber se te afeta.
Achado realSBOM do repo real = 40 componentes em CycloneDX, incluindo GitHub Actions do CI — não só libs de linguagem.
Ações
implementadaGerei o SBOM do repo real e do app de lab em CycloneDX.→ 40 componentes (repo) / 2872 (imagem)
implementadaSimulei uma CVE hipotética em anyio < 4.16.0 e consultei o sbom.json já gerado em vez de re-escanear a imagem.→ anyio 4.15.1 achado em milissegundos
implementadaConfirmei no PR #1 que o job de SBOM roda no CI e publica o artefato CycloneDX a cada build.→ verde no CI
Vs. vaga da Casey (Analog Devices) citada explicitamente — peso extra SBOM está no anúncio, e aqui pesa mais que boa prática genérica: a ADI tem linha regulada como SaMD (Software as a Medical Device), e a FDA exige SBOM na submissão de software médico desde 2023 — pra esse produto específico é requisito regulatório, não opcional.
sem inventário→40 componentes catalogados
06OWASP ZAP
DAST
DAST = Dynamic Application Security Testing — ataca a aplicação já rodando, de fora, simulando um atacante real; nunca olha o código-fonte.
Como funcionaSobe um proxy que primeiro navega pela app (spider/crawl) descobrindo rotas, depois manda os requests capturados de volta com variações (headers ausentes, payloads simples) e audita as respostas — tudo via HTTP, de fora.
Como eu usoSubo a app com docker run, depois docker run zaproxy/zap-stable zap-baseline.py -t http://host.docker.internal:PORT/ — o "baseline" é o modo rápido e majoritariamente passivo, não-destrutivo.
ResolveFalha que só existe com a app rodando de verdade (headers, config de runtime) — invisível lendo o código-fonte.
Achado realapp.py de 12 linhas, sem nenhum bug de lógica, ainda assim com 3 headers de segurança ausentes em runtime.
Ações
implementadaMiddleware adicionando X-Content-Type-Options, Cross-Origin-Resource-Policy e Cache-Control.→ 3 → 1 WARN
implementadaRodei o ZAP no CI (PR #1). O scan bateu com o local (66 PASS, 1 WARN, 0 FAIL); o job falhou 2× por config: token sem issues: write (→ allow_issue_writing: false) e upload de artefato na API aposentada (→ action-baseline@v0.15.0).→ verde no CI
decisão: não fazerScan autenticado — a app não tem autenticação; adicionar só pra testar a ferramenta seria inflar escopo. O WARN residual é efeito esperado do próprio fix.
Vs. vaga da Casey (Analog Devices) citada explicitamente DAST está no anúncio ao lado de SAST/SCA/SBOM — fecha o quarteto de siglas que motivou o crash course inteiro.
3 WARN→1 WARNresidual é efeito esperado do próprio fix
