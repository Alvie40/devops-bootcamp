DevSecOps crash course — 17–18/09/2026

Achado → mitigação, ferramenta por ferramenta

Cada linha é uma ferramenta rodada de verdade contra código/dependências/imagem/app reais neste crash course — o problema que ela existe pra resolver, o que apareceu na prática, e a correção aplicada e reverificada com a própria ferramenta.

01Gitleaks
Secrets
ResolveCredencial hardcoded commitada no git — some do arquivo, mas não do histórico.
Achado real0 leaks no repo real. Demo provocada (repo git descartável): removi a chave num commit "fix" e o Gitleaks ainda achou, apontando o commit antigo — git show confirmou que a chave inteira ainda existe lá.
Ações
implementadaRodei o Gitleaks contra o histórico real e provoquei um leak num repo descartável pra confirmar o comportamento.→ 0 leaks reais, causa raiz explicada
pendenteInstalar como pre-commit hook no repo (hoje só roda manual) e rotacionar uma credencial de verdade após um leak.
leak provocado→detectado + causa raiz explicada
02Semgrep
SAST
ResolveBug de segurança no código que você mesmo escreveu (injection, hash fraco, secret hardcoded).
Achado realRuleset padrão (auto) pegou 3 de 4 bugs plantados — perdeu os.system("..."+var), mesma classe de subprocess.call(shell=True), só com sintaxe diferente.
Ações
implementadaEscrevi uma regra Semgrep própria em YAML (pattern: os.system("..." + $VAR)) fechando exatamente o gap.→ 3 → 4 findings
pendenteAplicar os padrões de fix no código real (sem shell=True, hash com scrypt/bcrypt, secret em variável de ambiente) — hoje só existem no arquivo de demo.
3 findings→4 findings
03Trivy fs
SCA
ResolveCVE conhecida em biblioteca de terceiros que o projeto importa — não é código seu, mas é seu risco.
Achado realrequests==2.6.0 / pyyaml==5.1 / urllib3==1.24.1 → 20 CVEs (3 críticas), incluindo RCE no PyYAML via FullLoader.
Ações
implementadaPinei versão corrigida exata (==) de cada lib e reescaneei.→ 20 → 0 CVEs
implementadaDescobri que range (>=) faz o Trivy nem escanear — só versão fixa funciona.→ virou regra pro time
pendenteConfigurar Dependabot/Renovate no repo real pra manter isso automático, e o gate do CI ainda não rodou contra um PR de verdade.
20 CVEs→0 CVEs
04Trivy image
Container
ResolveVulnerabilidade herdada da imagem base (SO + libs de sistema) — invisível olhando só o código da app.
Achado realpython:3.11 completo = 654 CVEs críticas/altas, quase tudo do Debian base (não da app).
Ações
implementadaTroquei a base pra -slim.→ 654 → 62
implementadaAtualizei fastapi (puxou starlette sem CVE).→ 62 → 59
implementadaTentei atualizar pip/setuptools/wheel pra fechar as 2 CVEs restantes do Python.→ trocou por outras 2, sem ganho — revertido
pendenteMulti-stage build / distroless pra remover perl/util-linux não usados pela app (3 CRITICAL residuais) e agendar rebuild periódico pra pegar patch da base image.
654→593 CRITICAL residuais no SO (Perl não usado pela app)
05Syft
SBOM
ResolveSem inventário, uma CVE nova (ex.: Log4Shell) exige re-escanear tudo do zero pra saber se te afeta.
Achado realSBOM do repo real = 40 componentes em CycloneDX, incluindo GitHub Actions do CI — não só libs de linguagem.
Ações
implementadaGerei o SBOM do repo real e do app de lab em CycloneDX.→ 40 componentes catalogados
pendenteSimular uma CVE nova de verdade e consultar o SBOM pra responder em minutos (nunca fiz esse exercício), e confirmar que o job de CI publica o artefato a cada build.
sem inventário→40 componentes catalogados
06OWASP ZAP
DAST
ResolveFalha que só existe com a app rodando de verdade (headers, config de runtime) — invisível lendo o código-fonte.
Achado realapp.py de 12 linhas, sem nenhum bug de lógica, ainda assim com 3 headers de segurança ausentes em runtime.
Ações
implementadaMiddleware adicionando X-Content-Type-Options, Cross-Origin-Resource-Policy e Cache-Control.→ 3 → 1 WARN
pendenteConfigurar scan autenticado (hoje só cobre rota anônima); o WARN residual é efeito esperado do próprio fix — decisão consciente, não pendência.
3 WARN→1 WARNresidual é efeito esperado do próprio fix
